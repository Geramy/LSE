# Long-context KV growth on R9700

## Failure and change

The Qwen3.8-27B Q4 target with a Q8 DFlash2 draft failed near a 32,768-token
KV pool boundary. The affected session completed 32,170 total tokens. Its next
request returned `HSA_STATUS_ERROR_OUT_OF_RESOURCES` before generating a token.

A split prefill kept the preceding chunk's hidden computation graph alive while
building the next chunk. That graph and the scheduler's retained program held
references to the old paged KV buffers during growth. The generator now drops
the consumed hidden graph before each chunk, and the model releases the
scheduler program when the pool must move. It also drops redundant paged
key/value references in the mixer state. A short instrumented run showed two
old KV node references after replacement before these changes and zero after.

For pools above 2,048 blocks, growth now adds 256 blocks per rung rather than
doubling. With 16 tokens per block, each rung reserves up to 4,096 more token
positions. This bounds temporary allocation pressure at long context. The KV
format remains BF16, and attention accumulation remains FP32. More frequent
growth can add occasional pool copies and kernel compilation at rung crossings.

## GPU test

The local R9700 test used the Q4 target, Q8 DFlash2 draft, Loom on HRX, BF16
KV, batch and microbatch 1024, temperature 0.6, top-k 20, top-p 0.95 and seed
1234. The server advertised a 262,100-token KV limit. One HTTP process served
successively longer prompts with a common prefix. Each growth request produced
one token so the next request could reuse the cached prefix. Driver counters
were sampled during the run.

| Prompt tokens | Cached tokens | Result | New-token prefill |
| ---: | ---: | --- | ---: |
| 30,726 | 0 | Completed | 327.2 tok/s |
| 33,126 | 30,726 | Completed | 150.1 tok/s |
| 37,126 | 33,126 | Completed | 128.9 tok/s |
| 41,126 | 37,126 | Completed | 116.0 tok/s |
| 65,354 | 41,394 | Completed | 90.3 tok/s |

The four-turn run through 41,126 tokens peaked at 28.37 GB of reserved device
memory. The extension to 65,354 tokens peaked at 29.72 GB and had at least
4.22 GB free at sampled points. A 32-token DFlash2 continuation at 65,394
prompt tokens completed with 96.3% proposal acceptance and 11.7 tok/s across
31 timed decode tokens. Reserved device memory changed by about 0.5 MB across
that decode request.

An intermediate build with smaller growth rungs but retained graphs completed
33,126 tokens and failed on the 37,126-token request while allocating 80 MiB.
The combined ownership and growth changes were needed for this test.

The clean candidate generated exactly the same 128-token response as the saved
v0.4.18 control for a seeded 8,192-token prompt. It measured 538.4 prompt
tok/s and 29.8 decode tok/s on that shorter check. The CPU runtime suite passed
74 tests with 6 skipped.

## Limits

The long prompts repeat a short synthetic sequence. Their near-certain draft
acceptance and decode rate do not predict real conversation speed. Driver
counters measure reserved allocations and sampling can miss an instantaneous
peak. This test verifies operation through 65,394 prompt tokens on this GPU;
the configured 262,100-token limit is not a measured usable capacity. Longer
contexts need separate memory and throughput measurements.
