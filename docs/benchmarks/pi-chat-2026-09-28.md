# Pi chat performance investigation — 2026-09-28

## Workload

Radeon AI PRO R9700, gfx1201, macOS, Qwen3.8-27B Q4 target,
Q8 DFlash2, verification depth 3, FP32 KV, maximum KV length 262100.
The HTTP client streams two ordinary chat turns with Pi's seven tool schemas
and low thinking effort. The first prompt contains 5207 tokens. Each request
allows up to 2048 generated tokens and stops naturally.

The baseline reproduces the user's original 66 and 265 generated tokens,
including the same reasoning and answer text, and the same proposal acceptance.
The decoder timing excludes the first token, which comes from prefill.
No wait-policy override is set. `LSE_TIME_SPANS=1` collects built-in timing spans.
No dispatch serialization or repeated identical prompt warm-up is used.

## Prompt prefix fix

The baseline reconstructs assistant history by adding a newline after
`reasoning_content`, even when that field already ends with a newline.
This changes the token prefix and causes the resident session to restart.
The fix preserves the existing reasoning newline.

| Measure | Baseline bdce408 | Prefix fix 5903e43 |
|---|---:|---:|
| First-turn prefill | 18.308 s | 18.387 s |
| First-turn decode | 16.318 tok/s | 16.097 tok/s |

These are individual request measurements. The user's reported 57.77-second
second prefill was slower than this reproduction; this result does not explain
that entire difference. Fixing serialization changes the context used by the
second answer, so its output and length can change. The prefix fix removes the
redundant prefill; it does not establish a decode throughput improvement.

## Sampling diagnosis

Pi sends no temperature, top-k or top-p value in these requests. The old HTTP
fallback is temperature 1, top-k 0 and top-p 1. The checkpoint's
`generation_config.json` specifies temperature 1, top-k 20 and top-p 0.95.

The old unfiltered sampler sorts all 248320 logits for every sampled token.
A CPU profile attributes 97.3% of samples in the isolated baseline to introsort.
A finite-logit linear sampling path reduces the measured component cost from
12.796 ms to 0.721 ms per call. It retains the mathematical softmax weights and
one random draw, but changes the unfiltered same-seed token sequence because
CDF intervals are in token order. Filtered sampling keeps its previous code.
The model's top-k 20 / top-p 0.95 path takes about 0.096 ms per call already.
These component measurements do not establish an HTTP speedup.

In the baseline second request, decode takes 13.882 s: verification 7.905 s,
drafting 2.243 s, and other work 3.735 s. Sampling is outside the draft and
verification timers and accounts for a substantial part of that remainder.
